# FPGA 资源与性能优化入门

整理日期：2026-11-18  
适用场景：理解 Vivado 资源占用表，以及判断 FPGA 性能应该从哪里优化。

## 1. 先回答：优化性能，主要优化什么？

**通常优先优化关键路径、流水线结构和数据供给能力，而不是把某一种资源的占用率降到最低。**

可以把 FPGA 理解成一条工厂生产线：

- LUT 是负责判断、选择、计算的小工位。
- FF 是工位之间暂存数据的格子。
- DSP 是专门做乘法、乘加的机器。
- BRAM / LUTRAM 是存放原料和中间结果的仓库。
- IO 是和工厂外面交换数据的通道。
- 布线是工位之间的运输路线，时钟负责协调各个工位的节奏。

工厂空地很多，不代表生产线一定快。同样，FPGA 资源只用了几个百分点，也可能因为某一段电路太长而跑不动目标频率。

## 2. “性能”要先分清三个指标

| 指标 | 直观含义 | 常见单位 | 主要受什么影响 |
|---|---|---|---|
| 时钟频率 | 每秒能走多少拍 | MHz | 关键路径延迟、时钟关系、器件能力 |
| 吞吐率 | 每秒能处理多少份数据 | 样本/秒、MB/s | 频率、并行度、启动间隔、访存和接口带宽 |
| 延迟 | 一份数据从输入到输出等多久 | 时钟周期、ns、μs | 流水线级数、排队、传输、计算结构 |

在处理单元持续有数据、输出不阻塞的条件下，可近似理解为：

```text
吞吐率 ≈ 时钟频率 × 并行通道数 ÷ 每通道启动间隔
计算延迟 ≈ 从输入到结果所需的周期数 ÷ 时钟频率
```

“启动间隔”指连续接收两份新任务之间，要隔多少拍。

例如：

- A：200 MHz，每 4 拍才能接收一份新数据，吞吐率约 5000 万份/秒。
- B：150 MHz，每拍都能接收一份新数据，吞吐率约 1.5 亿份/秒。

**B 的频率更低，但吞吐率更高。** 所以“提速”有时要提高频率，有时要减少等待或增加并行通道。

## 3. 时钟为什么会被一条路径卡住？

先看最常见的同一时钟、单周期寄存器到寄存器路径：

```text
起点 FF → 组合逻辑 → 连线 → 终点 FF
```

起点 FF 在时钟沿后输出数据，数据必须在下一个有效时钟沿到来前，提前稳定在终点 FF 的输入端。

忽略具体时钟树细节时，可以用下面的式子理解建立时间要求：

```text
时钟周期 ≥ 起点 FF 输出延迟
         + 组合逻辑延迟
         + 布线延迟
         + 终点 FF 建立时间
         + 不确定度等余量
```

实际 Vivado 计算还会处理时钟偏斜、时钟关系和时序例外，不能把这个简式套到所有跨时钟或多周期路径。

例如，200 MHz 的周期是 5 ns。如果某条路径连同相关开销需要 6 ns，这条路径就无法满足该目标。其他电路即使很空闲，也不能替它省出时间。

**关键路径就是当前时序要求下余量最差的路径。** 对同一时钟、同一要求的一组路径，它通常就是最拖慢速度的那条路径；跨时钟或不同约束之间，不能只比绝对数据延迟。

## 4. 各种资源怎样影响速率？

没有通用的“LUT 第一、BRAM 第二、DSP 第三”排名。应该看哪种资源位于关键路径上，以及它的连接方式。

| 资源 | 容易影响速度的情况 | 常见优化方向 |
|---|---|---|
| LUT | 串联逻辑层数多、宽位比较、大型选择器、复杂优先级判断 | 拆分计算、平衡逻辑结构、适当缩小位宽、插入流水线 |
| FF | 流水线不足导致单拍任务过重；控制信号负载过大 | 在合适位置增加寄存器，平衡各级工作量，减少不必要的全局控制 |
| DSP | 乘法/乘加集中在一拍，内部流水线没用起来，前后接了很多逻辑 | 利用内部寄存器，合理拆级，核对综合后的 DSP 映射 |
| BRAM | 读出后接长逻辑、输出未寄存；端口不够导致计算单元等待 | 启用适当的输出寄存器，调整存储分组和访问调度 |
| LUTRAM | 存储结构过大、地址/输出选择复杂，或读出后紧接长逻辑 | 根据容量、读写行为和时序需求选择 LUTRAM 或 BRAM |
| IO | 外部接口带宽不足，或输入输出时序要求难满足 | 优化协议效率、接口宽度/并行度、IO 寄存器和板级时序 |
| 布线与布局 | 模块距离远、高扇出、局部拥塞，导致连线延迟大 | 改善连接结构、局部复制驱动、适当流水线，再考虑布局约束 |
| 时钟资源 | 时钟关系、偏斜、不确定度或时钟结构不合理 | 使用合适的专用时钟资源，核对时钟及跨时钟约束 |

“扇出”就是一个信号要同时驱动多少个接收点。比如一个使能信号连到几千个寄存器，工具需要处理大量分支和长距离连接，可能形成时序或拥塞问题。

### 4.1 LUT：关注关键路径上的层数

下面两种情况，占用相同数量的 LUT，也可能有完全不同的速度：

```text
很多支路各自只经过少量 LUT：可能很快。
某条支路连续经过很多层 LUT：可能成为瓶颈。
```

常见问题包括：一拍里做多次依赖前一步结果的计算、多层条件选择、过宽的比较或算术运算。

优化时看综合后的实际电路和时序报告。RTL 行数少，不代表电路层数少；写成循环也不等于硬件会逐拍执行，综合可能将它展开成一大段组合逻辑。[参考：检查推断出的逻辑](https://docs.amd.com/r/en-US/ug949-vivado-design-methodology/Check-Inferred-Logic)

### 4.2 FF：多用一些，反而可能更快

增加 FF 经常是为了把长计算拆开，让每一拍只做一部分工作。这就是流水线，也常叫“打拍”。

```text
拆分前：FF → 运算 A → 运算 B → 运算 C → FF

拆分后：FF → 运算 A → FF → 运算 B → FF → 运算 C → FF
```

示意假设：原来三个运算的组合延迟合计 9 ns；拆分后，每一级约 3 ns。实际周期还要加寄存器、布线和时钟相关开销，因此不能直接认定一定达到 333 MHz。

流水线常见代价是：FF 增多、结果需要更多拍才出来，以及控制逻辑要跟着调整。如果各级都能每拍接收新数据，填满流水线后仍可每拍输出一份结果。

**打拍时必须让 data、valid、地址、标记等属于同一份任务的信号保持对齐。** 有 ready/valid 握手的电路还要处理停顿和反压，不能只给数据随手加一拍。

增加流水线通常有利于频率和吞吐率，但不保证单份数据的实际时间延迟更短，尤其在反馈计算或可变停顿结构中。[参考：如何判断是否需要流水线](https://docs.amd.com/r/en-US/ug949-vivado-design-methodology/Determine-Whether-Pipelining-is-Needed)、[流水线的取舍](https://docs.amd.com/r/en-US/ug949-vivado-design-methodology/Pipelining-Considerations)

### 4.3 DSP：重点是用法和流水线

DSP 是专用算术硬件，适合乘法、乘加等操作，但“用了 DSP”不等于自动达到高频。

如果乘法器前后还串着很多逻辑，或内部寄存器没有用起来，DSP 相关路径仍可能很慢。对于需要高频的运算，应结合允许的延迟使用合适的输入、中间和输出流水线，并检查综合结果是否映射成预期结构。

**DSP 用得少，只能说明占用少，不能说明计算性能好或差。** 某个只用了 3 个 DSP 的设计，也可能被其中一个 DSP 周边的路径卡住。[参考：DSP 与算术推断](https://docs.amd.com/r/en-US/ug949-vivado-design-methodology/Coding-for-Optimal-DSP-and-Arithmetic-Inference)

### 4.4 BRAM / LUTRAM：容量够，不代表供数够快

存储器要同时看两个问题：

1. **时序**：数据读出后，还要在这一拍内经过多少计算？输出有没有适当寄存？
2. **带宽**：每拍需要读写多少份数据？实际端口和调度能不能满足？

例如，4 个并行计算单元每拍各需要一个不同地址的数据，如果当前存储组织每拍只能提供 2 个所需数据，就会有人等待。即使 BRAM 容量还有很多空余，吞吐率也会被限制。

可能的办法包括分成多个独立存储组、在允许时复制只读数据、调整访问顺序或增加预取。具体选择取决于是否存在读写冲突、一致性要求和资源预算。

BRAM 的输出寄存器有助于改善相关路径时序，但会改变读出延迟，后面的控制信号也要相应调整。DSP 和 BRAM 位置相对固定，前后连接距离同样需要关注。[参考：专用硬件块路径优化](https://docs.amd.com/r/2025.1-English/ug949-vivado-design-methodology/Optimizing-Paths-with-Dedicated-Blocks-and-Macro-Primitives)

### 4.5 IO：看接口带宽与时序，不只看引脚数

IO 占用 9.75%，不意味着外部数据通道还剩 90.25% 的传输能力。这个比例主要体现输入输出资源的数量占用。

接口有效带宽取决于位宽、传输速率、协议开销和空闲等待。即使内部计算很快，输入供不上或输出排不出去，系统吞吐率仍然上不去。

外部存储器、串行收发器、控制器等还可能涉及这张表没有单独展示的资源，不能只靠 IO 一行判断整个接口能力。

## 5. 资源占用率究竟有什么用？

资源占用主要回答：**设计放不放得下，以及布局布线是否还有选择空间。**

- 低占用：有空间增加流水线、并行单元、局部缓存或必要的数据副本。
- 高占用：可选位置和布线路径减少，更容易出现拥塞，时序收敛可能变难。
- 总占用低：仍可能存在局部模块拥塞、长连接或高扇出。

因此，减少资源有时能改善布线，有时却因过度共享硬件而增加选择器、调度和等待，导致性能下降。

**不存在一个占用率阈值，能保证低于它就一定达到某个频率。** 资源、速度、功耗之间需要按目标取舍。[参考：AMD 时序收敛快速指南](https://docs.amd.com/api/khub/documents/l0_DOS3th0gXOZ8T2szPnA/content)

以下是截图中的估算值，不代表本次重新运行了项目综合或实现。

| 资源 | 估计用量 | 总可用量 | 占用率 |
|---|---:|---:|---:|
| LUT | 11,250 | 203,800 | 5.52% |
| LUTRAM | 263 | 64,000 | 0.41% |
| FF | 12,641 | 407,600 | 3.10% |
| BRAM | 46.50 | 445 | 10.45% |
| DSP | 3 | 840 | 0.36% |
| IO | 39 | 400 | 9.75% |

表头里的 Available 是总可用量，不是剩余量；LUTRAM 使用的是具备存储功能的 LUT，不能把这几行简单相加得到“总资源占用率”。

目前能判断的是：截图列出的资源总体余量很大。**仅凭这张图，不能判断实际最高频率、当前瓶颈，也不能断定应该先优化 BRAM 或 DSP。**

对这个占用水平，合理的起点是：

1. 明确想提高的是频率、吞吐率，还是降低单次处理延迟。
2. 查看布局布线后的时序报告，确认目标时钟是否满足。
3. 如果时序不满足，先定位最差路径，再决定改 RTL、流水线还是连接结构。
4. 如果时序满足但数据处理仍慢，检查每份任务的周期数、存储端口和接口等待。

不要因为 BRAM 占用率在表里最高，就先削减 BRAM。也不要为了节省 FF，把本来有用的流水线去掉。

## 7. 在 Vivado 里，先看哪些报告？

### 7.1 先看实现后的 Timing Summary

完成实现并打开布局布线后的设计（Open Implemented Design），运行 Report Timing Summary。综合后的报告适合早期发现结构问题；实际布线后的结果更适合判断最终时序。

优先认识这些字段：

| 字段 | 含义 | 怎么读 |
|---|---|---|
| WNS | 建立时间相关分析中的最差时序余量 | 小于 0 表示至少有路径不满足要求 |
| TNS | 各违规终点的最差负余量之和 | 0 表示该项没有负余量；不是把所有重复路径的负值相加 |
| Failing Endpoints | 时序不满足的终点数量 | 帮助判断问题集中在少量端点还是大范围存在 |
| WHS / THS | 保持时间相关的最差余量 / 总负余量 | 也要检查，不能只看 setup |
| Unconstrained Paths | 缺少相应时序要求的路径 | 需要判断是否漏了时钟或输入输出约束 |

WNS ≥ 0、TNS = 0，只说明相应建立时间检查通过；还要确认保持时间、脉宽等检查，以及约束覆盖情况。缺少约束时，报告看起来“全绿”也不等于已经验证了全部接口。

来源：[Timing Summary 的组成](https://docs.amd.com/r/2026.1-English/ug906-vivado-design-analysis/Details-of-the-Timing-Summary-Report)、[UG906 时序分析指南](https://docs.amd.com/api/khub/documents/HDyLdlWD8GEAPX8sDXG4eA/content)。

### 7.2 再点开最差路径，分清慢在哪里

重点看 Startpoint、Endpoint、时钟要求、Slack，以及 Data Path Delay 的组成：

| 报告里的现象 | 优先调查什么 |
|---|---|
| Logic / Cell Delay 高，逻辑层数多 | 单拍计算是否太复杂，是否需要拆级或优化逻辑结构 |
| Net / Route Delay 高 | 连接距离、高扇出、拥塞，以及不合理的布局限制 |
| 路径经过 DSP / BRAM | 内部/输出寄存器是否利用，前后是否堆叠过多逻辑 |
| 时钟要求异常、跨时钟路径余量很差 | 时钟定义、时钟关系、CDC 结构和约束是否正确 |

优化一条路径后，第二差的路径可能成为新的瓶颈，所以要迭代查看报告，而不是只处理一次。[参考：降低逻辑延迟](https://docs.amd.com/r/en-US/ug949-vivado-design-methodology/Reducing-Logic-Delay)

### 7.3 可复制的 Tcl 报告命令

以下命令在 Vivado Tcl Console 中使用，前提是已经打开相应设计。它们用于查看报告，不会自动修改 RTL 或约束。

```tcl
# 查看总体时序，并包含未约束路径信息
report_timing_summary -report_unconstrained

# 查看最差的 10 条最大延迟路径，主要用于建立时间分析
report_timing -delay_type max -max_paths 10

# 查看最差的 10 条最小延迟路径，主要用于保持时间分析
report_timing -delay_type min -max_paths 10

# 按模块查看资源，找出哪些模块占用较多
report_utilization -hierarchical

# 查看各时钟组的逻辑层数分布
report_design_analysis -logic_level_distribution

# 检查时序约束问题
check_timing

# 多时钟设计可继续查看时钟关系与跨时钟结构
report_clock_interaction
report_cdc
```

跨时钟检查依赖正确的时钟定义；report_cdc 主要做结构检查，不能替代时序分析和功能验证。具体选项以当前安装版本的 `help 命令名` 为准。[参考：report_timing 命令](https://docs.amd.com/r/2026.1-English/ug835-vivado-tcl-commands/report_timing)、[CDC 检查范围](https://docs.amd.com/r/2026.1-English/ug906-vivado-design-analysis/Overview)

## 8. 推荐的优化顺序

1. **定目标**：例如“保持每拍一份输入，把 100 MHz 提高到 150 MHz”，或“频率不变，让每 4 拍一份变成每拍一份”。
2. **留基线**：记录当前频率、WNS/TNS、处理周期数、吞吐率和资源占用，便于比较。
3. **核对约束**：确认主时钟、派生时钟、输入输出时序、跨时钟关系与真实硬件一致。
4. **找瓶颈**：时序问题看关键路径；吞吐问题看空等、端口冲突、反压和任务调度。
5. **改主要原因**：逻辑长就拆级，算术慢就核对 DSP 和流水线，供数不足就改存储组织，布线慢就查连接结构。
6. **验证修改**：检查功能、数值位宽、溢出、数据与控制对齐，以及复位和停顿行为；再重新综合、实现和比较报告。
7. **达到目标后停止无效压缩**：保留对时序有帮助的资源投入，按项目的面积、功耗和延迟预算取舍。

不要用随意放宽时钟、添加 false path 或 multicycle path 的方式掩盖真实违规。这些约束只应描述电路本来就成立的时序关系；把报表变绿不等于把电路变快。

## 9. 最容易记住的几句话

- **资源表回答“用了多少”，时序报告回答“能否按要求跑”，吞吐测试回答“实际每秒做了多少”。**
- **LUT 看关键路径上的逻辑层数，FF 看流水线是否合理，DSP 看运算映射与内部流水线，存储看时序和供数能力。**
- **布线延迟和时钟因素也很重要，它们不直接体现在截图这几行占用百分比里。**
- **资源少不一定快；合理增加寄存器、缓存或并行单元，往往是提高性能的办法。**
- **结合你这张图，下一步最有价值的信息是布局布线后的 Timing Summary 和关键路径详情。**
